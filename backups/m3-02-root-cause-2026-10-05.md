## 确定的根因

用户提供的 worker 日志明确显示 QuizDraftPayload 两次请求均为 finish_reason=length、tool_calls=0、content_length=0。ReviewModel.structured 因无法取得结构化结果而抛出 ModelError，quiz_jobs 将该异常统一转换为“模型或数据库请求失败，请稍后重试”。

链路为：配置确认 → 入队 → worker 领取 → 资料读取 → 出题计划成功 → 整卷候选输出达到长度上限 → 两次同预算重试失败 → ModelError → Job failed → 前端显示统一错误。

未进入候选确定性校验、语义复核、质量修复或草稿发布事务。此次异常并非草稿数据库写入失败。数据库中 schema_migrations 包含 001 至 009，worker 正常读取和更新任务。

首次启动的 KeyboardInterrupt 在导入 psycopg 时发生，与第二次启动后处理任务的输出截断是两件独立事件。

## 触发条件与代码缺口

- llm.py:286 的 build_review_model 没有传入 max_tokens；DeepSeek 非思考模式使用供应商默认 8K 输出预算。
- quiz_jobs.py 启动模型时仅覆盖 model_timeout；QUIZ_MODEL_TIMEOUT 是请求时间预算，不是输出长度预算。
- quiz_generation.py:71 一次生成整份试卷，包含每题题干、选项、答案、解析、得分点、失分点和引用。15 题可能超出默认预算。
- llm.py:59 的结构化重试仍使用相同请求预算，没有针对 length 扩容或拆分。
- quiz_jobs.py:257 不将 ModelError 作为可安全展示的分类错误，导致前端混淆模型与数据库问题。
- max_repairs=2 是后续计划/候选质量校验的修复额度；候选解析失败直接抛异常，无法进入后续质量修复。

当前默认预算依据：https://api-docs.deepseek.com/api/create-chat-completion/ （2026-10-05 查询，未设置时非思考模式默认 8K）。历史日志没有 token usage，因此原始两次请求的精确消耗未知。
